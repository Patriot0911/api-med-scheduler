# Перереалізація бекенду: що вирішити до першого ендпоінту

Скіл про **порядок і рамки**. Деталі: `nest-module-anatomy`, `nest-dto-validation`, `nest-authorization`, `typeorm-migrations` (переносні), `scheduler-lessons`, `scheduler-accounts` (доменні).

## 1. Що переписувалось і чому (з `git log` і міграцій)

| Що | Обсяг | Причина | Що запобігло б |
|---|---|---|---|
| Модель доступу до занять | 5 міграцій поспіль (`scoped-lesson-management` → `department-lesson-visibility` → `simplify-lesson-access` → `flatten-lesson-editing` → `lesson-departments`), коміти `rework lesson permissions` ≈ 1 300 рядків, `rework lessons module` ≈ 1 700 | правила доступу проєктувались разом з кодом, ітераціями | модель доступу на папері до коду (рішення 3) |
| Концепція дозволів | `rework permission concept`, `change routing based on permissions` ≈ 1 300, дозволи видалялись 3 рази | дозволи додавались під ендпоінти, а не з ролей домену | матриця ролей і дозволів до першого guard (рішення 2) |
| Auth | `session based auth` → видалено → JWT; потім logout за refresh-токеном | спершу не визначили модель сесії й клієнтів | модель токенів з урахуванням кількох акаунтів (рішення 4) |
| Enum дозволів у Postgres | `fix migration unsafe way to edit roles_permissions_enum` | `ALTER TYPE ... ADD VALUE` | патерн перестворення типу (рішення 7) |
| Фіча «перенесення заняття» | додано `delayedDate`, потім `drop-lesson-delayed-date` | фіча без чіткого сценарію | бізнес-сценарій перед схемою (рішення 1) |
| Фільтр помилок / env | `fix env parser & fix 500/404 exceptions filter` | конфіг і помилки не валідувались з початку | валідація конфігу й мапа помилок на старті (рішення 6) |
| Нотація | `add correction for code notation` | стиль не був закріплений у лінтері | правила в ESLint / Prettier (рішення 10) |

Що лишилось у коді досі: 500 на невалідному UUID у шляху (немає `ParseUUIDPipe`), різні повернення `PUT` (`boolean` vs item), однина / множина в назвах модулів (`semester`, `lesson`), camelCase-колонки у старих таблицях поруч зі snake_case, старий `@Req()` поруч із `@CurrentUser()`, чотири декоратори на кожному захищеному ендпоінті, 0 тестів.

## 2. Рішення дня нуль

1. **Бізнес-сценарії → сутності.** Для кожної сутності: хто створює, хто бачить, хто змінює, що відбувається при видаленні (`CASCADE` / `SET NULL`). Записати в `docs/domain.md` **до** entity.
2. **Матриця ролей і дозволів.** Дозвіл = доступ до групи ендпоінтів (`read_x` / `manage_x`), `admin` проходить усе. Дозвіл з'являється лише тоді, коли є роль, якій він потрібен окремо. Оголошені, але неперевірені дозволи (`read_comments`) не заводити.
3. **Три рівні авторизації — розділити одразу.** (а) доступ до ендпоінту — дозвіл; (б) дія над конкретним об'єктом — політика (ієрархія ролей, власність); (в) доменна участь (викладач заняття, завідувач) — окремий сервіс правил. Кожен рівень — свій сервіс, рішення повертається клієнту прапорцем (`canEdit`, `canManage`). → `nest-authorization`.
4. **Модель сесії.** Access + refresh з різними секретами; ротація refresh, хеш у БД; скільки активних сесій на користувача; logout за refresh-токеном (щоб завершувати неактивні акаунти клієнта); що відбувається з токенами при зміні ролей.
5. **Контракт відповіді.** `{ status, data }` інтерцептором, помилки `{ status: false, message: string | string[] }` фільтром; списки `{ items, meta: { count } }`; **одне** правило для повернень CRUD (рекомендовано: `POST` / `PUT` / `PATCH` → item, `DELETE` → item або кількість).
6. **Помилки й конфіг.** `EntityNotFoundError` → 404; глобальний `ParseUUIDPipe` для id у шляху (або `@Param('id', ParseUUIDPipe)`); валідація env на старті (тривалості, обов'язкові секрети в production).
7. **Схема й міграції з першого дня.** Конвенції імен (таблиці snake_case у множині, колонки snake_case, явні імена `FK_` / `UQ_` / `IDX_`); `synchronize` вимкнений **і в dev** (інакше dev-БД розходиться з міграціями, `migration:generate` дає порожній diff); enum-и Postgres змінюються перестворенням типу. → `typeorm-migrations`.
8. **Анатомія модуля.** models (інтерфейси) ↔ DTO (класи, `implements`), mapper, сервіс приймає / повертає інтерфейси. Однина / множина назв модулів — одне правило. → `nest-module-anatomy`.
9. **Складений декоратор авторизації.** `@Auth(...permissions)` = `applyDecorators(ApiBearerAuth(), UseGuards(JwtAccessGuard, PermissionsGuard), Permissions(...))` замість чотирьох рядків на ендпоінт.
10. **Інструменти.** Prettier (`singleQuote`, `trailingComma: all`), ESLint без `any` (`@typescript-eslint/no-explicit-any: error`), абсолютні імпорти між модулями. Перевірка типів — `npx tsc --noEmit`.
11. **Тести там, де логіка.** Unit-тести політик (`AuthorityService`, `LessonAccessService`: таблиці «actor × lesson → дозволено?»), e2e для auth-потоку. Без них кожна переробка моделі доступу перевіряється вручну.
12. **Документ домену живий.** `docs/domain.md` — джерело правди для обох репозиторіїв; змінюється в тій самій задачі, що й правило.

## 3. Порядок побудови

| Етап | Що | Готово, коли |
|---|---|---|
| 0. Каркас | Nest, конфіг з валідацією, TypeORM + docker-compose, інтерцептор, фільтр, `ValidationPipe` (`transform`, `whitelist`), Swagger, `ParseUUIDPipe` | `tsc --noEmit` і `lint` чисті, `/api/docs` відкривається |
| 1. Auth і ролі | users, roles, permissions enum, JWT access / refresh, guards, `@Auth`, seed адміна, `AuthorityService` | логін / refresh / logout, ієрархія покрита тестами |
| 2. Довідники | кафедри, групи, теги, семестри + `DictionariesModule` | кожен з CRUD, пагінацією, пошуком, довідником `{ id, name }` |
| 3. Профілі | teacher / student 1:1 до user, завідувач | `teacherId ≠ userId` скрізь у контрактах |
| 4. Ядро домену | заняття: сервіс правил, базовий сервіс, керований сервіс, адмін-контролери | правила з `domain.md` покриті тестами політики |
| 5. Серії й групи | групи занять, серії, масові дії, транзакції | ліміти (≤ 200) і транзакції описані в `domain.md` |
| 6. Публічне | `OptionalJwtAccessGuard`, видимість | анонім бачить лише `visibility = all` |

Кожен етап закінчується оновленням `docs/domain.md` (правила й карта ендпоінтів) і CLAUDE.md («Відомі пастки»).
